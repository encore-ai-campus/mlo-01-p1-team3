# BRD — 자동차 제조사 영업·고객지원 데이터 통합 솔루션

## 1. 프로젝트 개요

### 1.1 프로젝트명
**자동차 제조사 영업·고객지원 데이터 통합 솔루션**

### 1.2 프로젝트 배경

가상의 고객사는 전국 판매망을 운영하는 자동차 제조사이다.

현재 지역별 자동차 등록 현황과 같은 **시장 데이터는 외부 공공데이터를 통해 확인**하고 있으며, 차량 구매·정비·보증 등과 관련된 **고객 FAQ 데이터는 자사 웹사이트에서 별도로 관리**하고 있다.

이로 인해 영업팀과 고객지원팀이 서로 다른 데이터 소스와 관리 방식을 사용하고 있으며, 필요한 정보를 각 담당자가 개별적으로 확인해야 한다.

또한 데이터 수집과 갱신 과정에 대한 통합 관리 체계가 없어 운영 담당자가 데이터가 정상적으로 갱신되었는지 확인하기 어렵다.

본 프로젝트는 서로 다른 형태와 출처를 가진 시장 데이터와 고객지원 데이터를 각각의 특성에 맞게 수집·정제·검증·저장하고, 각 부서에서 필요한 정보를 효율적으로 조회할 수 있는 데이터 통합 환경을 구축하는 것을 목적으로 한다.

---

# 2. 문제 정의

현재 고객사는 다음과 같은 문제를 가지고 있다.

### 2.1 시장 데이터 분산

지역별 자동차 등록 현황은 외부 공공데이터를 통해 별도로 확인해야 한다.

영업 담당자가 특정 지역의 자동차 시장 규모나 차량 유형별 등록 비중을 확인하려면 데이터를 직접 조회하고 가공해야 하므로 반복적인 업무가 발생한다.

예를 들어 영업 담당자가 다음과 같은 정보를 확인하고자 할 수 있다.

> "경기도에서 SUV 등록 비중이 높은 지역은 어디인가?"

현재는 해당 질문에 답하기 위해 외부 데이터를 직접 확인하고 별도의 가공 과정을 거쳐야 한다.

### 2.2 고객지원 데이터 조회의 비효율

고객 FAQ는 자사 웹사이트에서 관리되고 있으나 구매, 정비, 보증 등 다양한 유형의 문의가 하나의 데이터 소스에 존재한다.

고객지원 담당자는 필요한 FAQ를 빠르게 조회하거나 특정 카테고리의 문의 내용을 파악할 수 있는 데이터 조회 환경이 필요하다.

예를 들어 다음과 같은 요구사항이 존재한다.

> "차량 구매, 정비, 보증 카테고리의 FAQ를 빠르게 조회하고 싶다."

### 2.3 데이터 갱신 상태 확인의 어려움

시장 데이터와 FAQ 데이터가 정상적으로 수집 및 저장되었는지 확인하기 위한 통합적인 운영 정보가 부족하다.

운영 담당자는 다음과 같은 정보를 확인할 수 있어야 한다.

> "매월 데이터 갱신이 정상적으로 수행되었는가?"

따라서 데이터 수집 성공 여부, 처리 건수, 오류 발생 여부 등의 운영 정보를 확인할 수 있는 관리 체계가 필요하다.

# 3. 프로젝트 목표

본 프로젝트의 목표는 다음과 같다.

1. 외부 자동차 등록 데이터를 정기적으로 수집하여 지역별 자동차 시장 현황을 조회할 수 있는 환경을 구축한다.
2. 여러 제조사의 FAQ 데이터를 수집하여 카테고리별 고객 문의 정보를 효율적으로 조회할 수 있도록 한다.
3. 서로 다른 데이터 소스를 공통적인 데이터 처리 흐름을 통해 관리한다.
4. 수집된 데이터의 형식 및 필수 값 등을 검증하여 데이터 품질을 확보한다.
5. 데이터 특성에 따라 적절한 데이터베이스에 저장한다.
6. 영업팀, 고객지원팀, 운영팀이 각자의 업무 목적에 맞게 데이터를 조회할 수 있도록 한다.
7. 데이터 갱신 결과와 오류 발생 여부를 기록하여 운영 상태를 추적할 수 있도록 한다.

# 9. Business Rules

## 9.1 시장 데이터

**BRULE-01**  
지역 정보가 존재하지 않는 자동차 등록 데이터는 정상 데이터로 처리하지 않는다.

**BRULE-02**  
차량 유형 정보가 존재하지 않는 데이터는 분석 대상에서 제외하거나 오류 데이터로 기록한다.

**BRULE-03**  
자동차 등록 대수는 숫자로 변환 가능한 데이터만 정상 데이터로 처리한다.

**BRULE-04**  
지역별 차량 유형 비중은 해당 지역 전체 자동차 등록 대수를 기준으로 계산한다.

예:

SUV 등록 비중  
= 특정 지역 SUV 등록 대수 / 해당 지역 전체 자동차 등록 대수

---

## 9.2 FAQ 데이터

**BRULE-05**  
FAQ는 최소한 카테고리와 질문 또는 제목 정보를 포함해야 한다.

**BRULE-06**  
필수 데이터가 존재하지 않는 FAQ는 정상 데이터와 구분하여 처리한다.

**BRULE-07**  
동일한 FAQ가 반복적으로 수집되는 경우 중복 데이터 여부를 확인한다.

---

## 9.3 Pipeline 운영

**BRULE-08**  
데이터는 수집 후 바로 저장하지 않고 정제 및 검증 단계를 거쳐야 한다.

**BRULE-09**  
검증에 실패한 데이터는 정상 데이터와 구분할 수 있어야 한다.

**BRULE-10**  
Pipeline 단계에서 오류가 발생한 경우 오류 발생 단계와 원인을 기록해야 한다.

**BRULE-11**  
Pipeline 실행 시 실행 시각과 성공 또는 실패 여부를 확인할 수 있어야 한다.

**BRULE-12**  
데이터 갱신 작업은 정해진 주기에 따라 반복적으로 수행할 수 있어야 한다.

# 10. 데이터 저장 전략

## 10.1 자동차 등록 데이터 — MySQL

자동차 등록 데이터는 다음과 같은 특성을 가진다.

- 지역
- 기준일
- 차량 유형
- 등록 대수

해당 데이터는 구조가 비교적 일정하며 다음과 같은 집계 및 조회가 필요하다.

- 지역별 등록 대수
- 차량 유형별 등록 대수
- 지역별 SUV 등록 비중
- 지역 간 등록 대수 비교

따라서 정형 데이터 관리 및 집계에 적합한 관계형 데이터베이스인 **MySQL**을 사용한다.

---

## 10.2 FAQ 데이터 — MongoDB

FAQ 데이터는 다음과 같은 정보를 포함할 수 있다.

- 카테고리
- 질문
- 답변
- 하위 카테고리
- 관련 정보

FAQ의 경우 카테고리나 추가 속성이 변경될 가능성이 있으며 문서 단위로 데이터를 관리하는 것이 적합하다.

따라서 문서 기반의 데이터 관리에 적합한 **MongoDB**를 사용한다.

---

# 11. 핵심 데이터 Pipeline

본 프로젝트의 공통 데이터 처리 과정은 다음과 같다.

## 11.1 Collect

외부 데이터 소스에서 데이터를 수집한다.

- 자동차 등록 공공데이터
- 자동차 제조사 FAQ 웹페이지

## 11.2 Clean

수집한 데이터를 분석 및 저장 가능한 형태로 변환한다.

예:

- 불필요한 문자열 제거
- 공백 제거
- 컬럼명 통일
- 숫자 데이터 변환
- FAQ 텍스트 정제

## 11.3 Validate

데이터가 정의된 품질 기준을 만족하는지 검증한다.

예:

- 필수 값 누락 여부
- 데이터 타입
- 등록 대수 범위
- 중복 여부
- FAQ 필수 필드 존재 여부

## 11.4 Store

검증을 통과한 데이터를 데이터 특성에 적합한 저장소에 저장한다.

- 자동차 등록 데이터 → MySQL
- FAQ 데이터 → MongoDB

## 11.5 Query

각 이해관계자가 자신의 업무 목적에 맞는 데이터를 조회한다.

### 영업 담당자

예:

> 경기도의 시·군별 SUV 등록 대수와 전체 자동차 대비 SUV 등록 비중을 조회한다.

### 고객지원 담당자

예:

> 정비 카테고리에 해당하는 FAQ를 조회한다.

### 운영 담당자

예:

> 금일 데이터 Pipeline이 정상적으로 실행되었는지 확인한다.

# 13. 제약사항 및 가정

## 13.1 제약사항

- 프로젝트는 실제 자동차 제조사가 아닌 가상의 고객사를 대상으로 한다.
- 개인정보를 포함한 실제 고객 데이터는 사용하지 않는다.
- 시장 데이터는 사용 가능한 외부 공공데이터 범위 내에서 구성한다.
- FAQ 데이터는 공개적으로 접근 가능한 웹페이지 또는 프로젝트용 샘플 데이터를 사용한다.
- 본 프로젝트에서는 대용량 실시간 데이터 처리를 대상으로 하지 않는다.

## 13.2 가정

- 자동차 등록 데이터는 지역 및 차량 유형을 구분할 수 있는 데이터를 제공한다고 가정한다.
- FAQ 웹페이지에는 카테고리, 질문, 답변 등의 정보를 식별할 수 있는 구조가 존재한다고 가정한다.
- 데이터 소스는 일정 주기로 접근할 수 있다고 가정한다.
- 시스템은 데이터 갱신 작업을 정기적으로 수행할 수 있는 실행 환경을 가지고 있다고 가정한다.

# 14. 기대 효과

### 영업팀
지역별 자동차 등록 데이터를 직접 가공하는 반복 업무를 줄이고, 시장 규모와 차량 유형별 비중을 기반으로 영업 전략 수립에 필요한 데이터를 빠르게 확보할 수 있다.

### 고객지원팀
FAQ 데이터를 카테고리별로 조회함으로써 필요한 고객지원 정보를 빠르게 탐색할 수 있다.

### 운영팀
데이터 수집부터 저장까지의 Pipeline 실행 결과를 확인함으로써 데이터 갱신 실패와 데이터 품질 문제를 추적할 수 있다.

### 조직 전체
서로 다른 데이터 소스를 개별적으로 관리하는 방식에서 벗어나 **수집 → 정제 → 검증 → 저장 → 조회**라는 일관된 데이터 관리 프로세스를 구축할 수 있다.

# 16. 참고

## 16.1 ID 부여 기준

본 문서의 요구사항 및 규칙은 추적성과 관리 편의를 위해 다음 기준으로 식별자를 부여한다.

| 구분 | ID 형식 | 의미 |
|---|---|---|
| Business Requirement | BR-XX | 비즈니스 요구사항 |
| Business Rule | BRULE-XX | 업무 및 데이터 처리 규칙 |

### 예시

- `BR-01`: 첫 번째 비즈니스 요구사항
- `BR-09`: 아홉 번째 비즈니스 요구사항
- `BRULE-01`: 첫 번째 비즈니스 규칙
- `BRULE-12`: 열두 번째 비즈니스 규칙

ID는 문서 내에서 중복되지 않도록 순차적으로 부여한다.

요구사항이 삭제되더라도 기존 ID는 재사용하지 않으며, 새로운 요구사항에는 새로운 번호를 부여한다.
