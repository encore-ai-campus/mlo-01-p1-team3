## 1. 문서 목적

본 문서는 3일 안에 구현해야 하는 MVP의 비즈니스 흐름과 사용자 결과를 정의한다. 이번 MVP의 핵심은 업무용 분석 제품을 완성하는 것이 아니라, 외부 데이터를 정해진 주기로 안정적으로 가져와 저장하고 운영자가 처리 상태를 확인할 수 있게 하는 것이다.

## 2. 배경과 문제

중고차 판매 업무에는 현재 판매 가능한 매물, 지역별 자동차 등록 현황, 고객지원 FAQ가 함께 필요하다. 그러나 세 데이터는 서로 다른 형식과 갱신 주기를 가지며, 수집 실패나 저장 누락이 발생해도 한 화면에서 확인하기 어렵다.

현재의 문제는 다음과 같다.

- FAQ를 웹페이지에서 매번 확인해야 한다.
- 중고차 매물의 신규·변경 상태를 반복해서 확인해야 한다.
- 자동차등록현황보고는 매일 최신 월 응답을 받고, 한 응답의 모든 차량·용도 지표를 분해해 관리해야 한다.
- 수집·전처리·적재 중 어느 단계에서 문제가 발생했는지 확인하기 어렵다.
- DB와 백엔드에 직접 접근하면 운영 보안 경계가 흐려진다.

## 3. 데이터별 비즈니스 역할

| 데이터 | 업무 의미 | MVP 결과 |
|---|---|---|
| FAQ | 고객지원 담당자가 참고할 공식 안내 정보 | MongoDB에서 최신 FAQ를 조회할 수 있는 구조 |
| 중고차 매물 | 현재 판매 가능한 차량과 공급 상태 | SQL에서 최신 매물 상태를 확인할 수 있는 구조 |
| 자동차등록현황보고 | 지역·월별 자동차 시장 참고 지표 | SQL에서 월·지역·차량·용도별 수량을 누적하는 구조 |
| Pipeline 운영정보 | 데이터가 언제, 어디까지, 어떤 결과로 처리됐는지 | Dashboard·로그·Discord 알림 |

자동차등록현황보고는 중고차 구매 수요를 직접 의미하지 않는다. 지역 시장을 이해하기 위한 참고 지표이며, MVP가 자동으로 판매 지역이나 가격을 결정하지 않는다.

## 4. To-Be 데이터 흐름

```text
외부 Source
   │
   ├─ FAQ HTML 크롤링 ───────────────┐
   ├─ 중고차 API 호출 ───────────────┤
   └─ 자동차등록현황보고 API 호출 ──┤
                                      ▼
                         Backend Python Pipeline
                         Collect → Preprocess
                                  → Validate → Load
                                      │
                         ┌────────────┴────────────┐
                         ▼                         ▼
                       SQL                     MongoDB
                         │                         │
                         └────── 운영 로그 ────────┘
                                      │
                         Python Dashboard + Discord
```

수집·전처리·검증·적재는 별도 서버가 아니라 Backend 서버 안의 논리적 레이어와 Python 모듈로 분리한다. 따라서 MVP에서 Collector 서버, ETL 서버, 메시지 큐를 별도로 추가하지 않는다.

## 5. 핵심 업무 시나리오

### 5.1 FAQ 수집 및 갱신

1. Backend가 KST 기준 매일 09:00에 `http://192.168.0.51:4000/`의 FAQ 영역을 크롤링한다.
2. 수집 결과를 질문·답변·분류·출처·수집시각이 포함된 구조로 전처리한다.
3. 필수값과 식별자를 검증한다.
4. MongoDB의 동일 FAQ를 찾아 신규이면 Insert하고 변경되었으면 Update한다.
5. 수집·전처리·검증·적재 결과를 로직별로 기록한다.
6. 실패하면 정상 데이터의 임의 삭제 없이 로그를 남기고 Discord로 알린다.

### 5.2 중고차 매물 수집 및 갱신

1. Backend의 장기 실행 Python Worker가 1초마다 같은 Source의 중고차 API를 순차 호출한다. 동시 호출은 하지 않는다.
2. API 1회 응답의 최대 처리량은 500건으로 제한한다. 초기 데이터가 1만건이면 20회 호출을 1초 간격으로 수행하여 SQL에 Insert한다.
3. 초기 적재가 끝난 뒤에는 마지막 성공 Checkpoint(Sequence·수정시각·Cursor 등) 이후의 신규·변경 데이터만 요청하여 증분 업데이트한다.
4. API 응답의 브랜드·모델·소재지·딜러·업무영역을 각각 참조 테이블에 먼저 Upsert하고, 매물 본체는 참조 ID를 가진 `vehicle_listings`로 저장한다. 신규 매물은 Insert하고 변경된 매물은 `listing_id` 기준으로 Upsert한다.
5. 가격·상태·주행거리 등 변경 필드는 현재 최신값으로 유지한다.
6. 한 번의 응답에서 보이지 않았다는 이유만으로 매물을 임의로 판매완료 처리하거나 삭제하지 않는다.

### 5.3 자동차등록현황보고 수집

1. 매일 정해진 실행 시각에 등록현황보고 API를 1회 호출한다.
2. `start_dt=end_dt=YYYYMM`으로 요청하고, 남은 일일 3,000회 quota를 초과하지 않도록 호출 전 예약한다.
3. 응답의 `result_data.formList` 각 행에서 `date`, `시도명`, `시군구`를 읽는다.
4. `승용>관용` 등 결합된 지표를 차량구분·용도구분·수량의 개별 SQL Row로 모두 분해한다.
5. 동일한 월·시도명·시군구·차량구분·용도구분은 중복되지 않도록 Upsert한다.
6. 실행일의 호출량, 요청 월, 원천 행 수, 분해 Row 수, 적재 건수, 실패 원인을 `pipeline_runs`와 로그에 남긴다.

## 6. 운영자 시나리오

운영자는 Public IP를 가진 Bastion에 SSH로 접속한 뒤 Backend 또는 DB에 접근한다. Backend에서 실행 중인 Python Dashboard를 SSH 터널로 열어 다음을 확인한다.

- FAQ·중고차·자동차등록현황보고 Pipeline의 마지막 실행 상태
- 시작·종료 시각과 수집·처리·Insert·Update·Reject 건수
- 자동차등록현황보고의 당일 API 호출량과 남은 예산
- 현재 실행 중인 단계와 마지막 오류
- SQL·MongoDB 연결 상태
- Discord 알림이 발생한 실패 Run의 원인

오류가 발견되면 Backend가 민감정보를 제거한 요약을 Discord Webhook으로 전파한다. Discord는 원본 데이터 전달 수단이 아니다.

## 7. MVP와 2단계의 경계

### MVP에 포함

- 세 데이터 Source 수집
- 수집 → 전처리 → 검증 → 적재 레이어
- FAQ MongoDB Upsert
- 중고차 SQL 초기 Insert 및 이후 Upsert
- 자동차등록현황보고 일일 1회 수집·3,000회 quota 보호·formList 지표 분해
- SQL 운영 로그와 실행 이력
- Backend Python Dashboard
- 오류 Discord 알림
- Bastion 경유 접근 통제
- SQL 복제 및 MongoDB 3노드 Replica Set 확장을 고려한 키·접속 구조

### 2단계로 미룬다

- 영업 담당자용 검색·추천·분석 화면
- 고객용 FAQ 서비스와 AI 자동응답
- SQL Master–Slave 실제 복제와 자동 Failover
- MongoDB 3개 서버 구성, Replica Set 선출·투표 운영
- 대용량 분산 처리, 메시지 큐, 데이터 웨어하우스
- 계약·결제·CRM·Billing 기능

## 8. 성공 상태

MVP는 다음 질문에 운영자가 답할 수 있으면 성공으로 본다.

1. 세 Pipeline이 정해진 주기로 실행되는가?
2. 중고차가 1초 주기·500건 단위로 수집되고, 동일 데이터 재수집에도 중복되지 않는가?
3. 자동차등록현황보고가 매일 1회 호출되고 응답의 모든 지표가 중복 없이 분해·적재되는가?
4. 각 단계의 성공·실패와 건수를 확인할 수 있는가?
5. 이슈가 발생하면 Backend 로그와 Discord에서 원인을 확인할 수 있는가?
6. DB와 Backend가 Bastion 경계를 벗어나 외부에 노출되지 않는가?

## 9. 선행조건과 위험

- AWS Backend에서 사설 주소 `192.168.0.51:4000`으로 통신할 수 있는 VPN, 전용 회선 또는 허용된 라우팅이 필요하다.
- Source의 FAQ 경로와 중고차 API 파라미터·Pagination 규격을 착수 시 확인해야 한다.
- 중고차 API가 초당 1회 호출, 1회 500건, 증분 기준값을 지원해야 한다.
- 자동차등록현황보고 API 인증키와 3,000회 한도 기준시각을 확인해야 한다.
- Discord Webhook 장애는 데이터 Pipeline의 성공·실패와 별도로 로그에 기록한다.
- 외부 Source가 응답하지 않으면 임의의 샘플 데이터를 운영 DB에 적재하지 않는다.
