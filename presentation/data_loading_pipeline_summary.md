# 데이터 적재 파이프라인 발표 요약

## 1. 전체 흐름

이번 데이터 파이프라인은 자동차 정형 데이터와 기업 FAQ 비정형 데이터를 분리해 저장하도록 구성했습니다.

```text
자동차 API → 정규화 → MySQL 초기 적재 → 변경분 증분 적재
기업 FAQ 웹페이지 → HTML 파싱·필수값 검증 → MongoDB 적재
```

## 2. 자동차 초기 적재

대상 파일: `load_cars_initial.py`

- 자동차 API에서 최신순 데이터를 페이지 단위로 수집합니다.
- 페이지당 100건, 최대 100페이지로 최신 차량 최대 10,000건을 초기 적재합니다.
- 자동차 정보는 MySQL `cars` 테이블에 저장하고, 영업소·딜러 정보는 외래키 관계를 고려해 `business_areas` 테이블에 먼저 저장합니다.
- `car_id`와 `listing_number`를 기준으로 UPSERT를 적용해 중복 적재를 방지합니다.
- 페이지 단위로 commit해 처리 단위를 관리하고, 실행 결과는 `crawl_logs` 테이블에 수집·신규·수정·실패 건수와 상태로 기록합니다.

**발표 문장**

> 초기 적재 단계에서는 최신 자동차 데이터를 최대 10,000건까지 수집하고, 정규화 후 MySQL의 영업소와 차량 테이블에 관계형 구조로 저장했습니다. 중복 데이터는 UPSERT로 처리하고, 실행 결과는 별도 로그 테이블에 남겨 적재 이력을 관리했습니다.

## 3. 자동차 변경분 적재

대상 파일: `update_cars_incremental.py`

- `crawl_logs`의 가장 최근 성공 실행 기록에서 `last_seq`를 읽어 checkpoint로 사용합니다.
- Changes API를 `after_seq` 기준으로 조회해 마지막 처리 이후의 변경 이벤트만 수집합니다.
- 변경 이벤트에서 차량 ID를 추출한 뒤 차량 상세 API를 다시 호출해 최신 차량 정보를 확보합니다.
- 초기 적재와 동일하게 영업소를 먼저 UPSERT하고 차량을 UPSERT합니다.
- 차량 한 건마다 commit하므로 일부 오류가 발생해도 이미 성공한 변경분은 유지됩니다.
- 성공 처리한 가장 큰 sequence를 `crawl_logs.last_seq`에 저장해 다음 실행이 이어서 처리할 수 있습니다.
- 기본 설정은 5분 간격 반복 실행이며, 실패가 있으면 `PARTIAL_SUCCESS` 상태와 실패 건수를 기록합니다.

**발표 문장**

> 증분 적재 단계에서는 마지막 성공 sequence를 checkpoint로 관리합니다. 이를 기반으로 변경된 차량만 조회하고 UPSERT하여, 전체 데이터를 다시 적재하지 않고도 5분 단위 최신화를 수행하도록 설계했습니다.

## 4. FAQ MongoDB 적재

대상 파일: `load_faqs_mongodb.py`

- 기업 FAQ 웹페이지를 요청하고 HTML에서 FAQ 항목을 파싱합니다.
- `faq_id`, 질문, 답변이 없는 항목은 저장하지 않아 기본 데이터 품질을 보장합니다.
- FAQ의 브랜드, 카테고리, 질문, 답변, 원본 URL, 검토 시각, 크롤링 시각을 문서 형태로 구성합니다.
- MongoDB Replica Set URI를 환경변수 `MONGO_URI`로 주입받아 연결할 수 있습니다.
- `faq_id` unique index를 생성하고 이를 기준으로 UPSERT하여 중복을 방지합니다.
- 브랜드와 카테고리 index를 생성해 FAQ 검색 성능을 고려했습니다.
- 수집·신규·수정·실패 건수를 콘솔에 출력하고 연결 종료를 처리합니다.

**발표 문장**

> FAQ는 질문과 답변처럼 구조가 유연한 비정형 데이터이므로 MongoDB에 저장했습니다. FAQ 고유 ID를 기준으로 UPSERT하고, 브랜드와 카테고리 인덱스를 추가해 중복 방지와 조회 성능을 함께 고려했습니다.

## 5. 설계 효과

- 정형 자동차 데이터는 MySQL, 비정형 FAQ 데이터는 MongoDB로 분리해 데이터 특성에 맞게 저장했습니다.
- 초기 적재와 증분 적재를 분리해 최초 구축 이후에는 변경 데이터만 효율적으로 처리합니다.
- UPSERT와 실행 이력 로그를 적용해 중복 적재를 줄이고, 실패 여부와 처리 건수를 추적할 수 있습니다.
- 이후 ETL 서버의 cron 또는 APScheduler에서 초기 적재는 1회 실행, 증분 적재는 주기 실행 방식으로 연결할 수 있습니다.

## 6. 발표 시 유의 사항

- 현재 세 스크립트의 API 기본 주소는 `192.168.0.51:4000`으로 작성돼 있으므로, EC2 운영 전에는 실제 API 주소를 환경변수 또는 운영 설정으로 분리해야 합니다.
- MongoDB 운영 환경에서는 `MONGO_URI`에 Replica Set 전체 URI와 인증 정보를 넣어야 합니다.
- 이 문서는 코드 구조를 요약한 발표 자료이며, 실제 API·MySQL·MongoDB 연결 성공 여부는 별도 실행 검증이 필요합니다.
